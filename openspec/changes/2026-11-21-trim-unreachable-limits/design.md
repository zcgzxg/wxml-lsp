# Design

## 判定规则

一个上限只在同时满足“不可达”这一条时才删；判断不可达的依据是上游已有更早、更粗的边界，而不是主观估计。保留项必须能指出它保护的真实资源。

1. **输入大小只在 I/O 边界限一次。** 单文件由 `files::MAX_FILE_BYTES = 16 MiB` 限定（磁盘读取、overlay、sources 共用）；stdio 入站由 `jsonrpc::MAX_MESSAGE_BYTES = 8 MiB` 限定。之后的字节/token/成员/类名数量上限不构成额外保护。
2. **深度上限只在真实递归处保留。** `MAX_ELEMENT_DEPTH`、表达式解析深度、组件解析递归守的是调用栈；迭代扫描里的“深度”不是保护，删。
3. **可达的数量上限是产品决定，只留一个执行点。** 用户真能触发的上限（补全条数、诊断条数、定义目标数）保留，但不能在 3～5 处各封一次。
4. **触发时静默产出错误结果的上限，优先删上限而不是补状态。** 例如模板元素绑定数超限丢掉整棵子树、注册脚本只读前缀。

## 删除与“补反馈”的取舍

备选方案是为每个超限补 `truncated`/`issue`/日志，让用户知道结果不完整。否决理由：

- 上限不可达，补的状态永远不会出现，是纯死代码；
- 可达且静默丢数据的上限，正确做法是不要那道截断，而不是把截断解释得更清楚；
- 用户明确要求不引入降级/兜底路径。

因此本变更不新增任何错误类型、状态字段或日志。

## 公开 API 的影响面

`WxsSummary::truncated` 被删除后，`wxml-lsp` 的 `index_incomplete` 与 hover 文案随之消失。`wxml-types` 的 `MAX_WXS_*` 等常量仅 crate 内部引用，删除不影响下游。`MAX_COMPLETION_ITEMS`、`MAX_SYMBOL_*`、`MAX_DOCUMENT_SYMBOL*` 有跨 crate 生产引用，保留并在去重时作为唯一定义。

## 明确不做

- 不改变入站 8 MiB 超限即终止 stdio 会话的行为（这是独立的协议 bug）。
- 不改变 `MAX_SHADOW_NAMES` / `MAX_IMPORT_SCAN_TOKENS` 把溢出误报为“shadowed identifier”的语义问题。
- 不删除 type-asset 的多层校验，除非能证明完全重复。
- 不新增资源限制策略 ADR；本文件即本次判定的记录。
