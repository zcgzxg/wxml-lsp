# ADR-0005：项目文档自包含与证据本地化

**日期**：2026-11-15
**状态**：accepted
**决策者**：项目维护者

## 背景

项目的功能需求和实验结论原先部分引用外部插件 README、外部仓库，以及本机临时实验目录。这些引用有三个问题：

1. 临时目录可能被清理，链接失效后需求无法追溯。
2. 外部仓库会更新、改名或改变许可证，旧结论不能稳定复现。
3. 需求文档应当能离线阅读；读者不应先安装或克隆另一个项目才能理解本项目要做什么。

同时，调研对象的版本、许可证和归属仍需保留，否则后续复用代码或元数据时缺少合规依据。实验也需要保留最小可复查材料，不能只留下“当时通过了”的结论。

## 决策

采用“本地需求基线 + 本地证据 + 隔离来源台账”的文档结构：

- 功能需求写入[WXML 语言功能基线](../reference/wxml-language-feature-baseline.md)，以本项目自己的行为、数据来源和验收条件表述。
- 实验结论、环境、方法、限制和最小数据写入 ADR、`docs/reference/` 或提交说明（由 [ADR-0009](0009-project-slimming.md) 更新）。临时目录和外部仓库不能作为唯一证据。
- 外部项目标识、版本、提交和许可证集中记录在[来源与许可证记录](../reference/provenance.md)，只用于归属、合规和复查，不作为需求入口。
- 架构决策引用本地需求和证据；需要引用外部对象时，通过来源记录定位。
- 临时实验在仓库外运行。进入仓库的只有决定保留的实现、样本、测试和结论。
- 文档中的本机绝对路径替换为相对链接或 `<probe-root>` 等占位符。

## 考虑过的替代方案

### 方案 A：继续只保留外部链接

- **优点**：维护量小，能直接指向原始材料。
- **缺点**：离线不可读；链接失效后无法判断需求来源；外部变更会改变语义；临时目录清理后证据消失。
- **未采用原因**：不满足“项目要求不能引用外部项目或文件”的约束。

### 方案 B：复制外部仓库和完整实验目录

- **优点**：材料齐全，短期可复查。
- **缺点**：仓库体积和许可证负担大；包含大量与结论无关的代码；外部代码进入项目后需要长期跟进；临时实验依赖的构建产物和依赖目录不适合入库。
- **未采用原因**：证据只需支撑结论，不需要复制整个调研对象。

### 方案 C：本地转写需求与最小证据（采用）

- **优点**：文档自包含、可离线阅读；许可证和归属仍可追溯；仓库体积可控；需求与实现验收直接对应。
- **缺点**：转写需要人工判断哪些行为是真正的需求；原始实验的部分细节可能丢失；必须明确证据等级。
- **采用原因**：在可读性、合规性和维护成本之间最平衡。

## 后果

### 正面

- 需求、功能基线和验收条件不再依赖外部项目是否存在。
- 临时目录被清理后，实验结论和最小数据仍可查阅。
- 外部来源的版本和许可证有单一台账，复用前有明确检查点。
- ADR、README、功能基线和证据之间的职责更清晰，减少重复和漂移。

### 负面

- 每次调研后需要额外整理和转写，不能只保存一个链接。
- 证据记录必须写明等级和限制；缺失脚本时要诚实标注，不能假装可复跑。
- 来源台账需要随复用行为更新，增加少量维护工作。

### 风险

- **转写丢失细节**：用原始输出、样本和明确的限制说明降低风险；关键实验保留运行脚本。
- **文档被误认为实现进度**：README 和证据记录继续区分“已验证”“已实现”“计划中”；`accepted` 不等于 implemented。
- **外部许可证变化**：复用前重新核对，不把来源记录当作永久授权。
- **新文档再次引用临时路径**：在评审和验证中搜索临时路径、绝对路径和外部项目标识，只允许出现在来源记录或证据对象说明中。

## 验证

- 需求文档和 ADR 中不出现以外部仓库或临时目录为唯一依据的表述。
- 所有功能要求都能在本地功能基线或项目 README 中找到。
- 每条证据记录包含对象版本、环境、方法、结果、限制和数据位置。
- 外部标识只出现在来源记录、证据对象说明和必要的归属文本中。
- 文档链接使用仓库相对路径，离线可读。
- ADR 索引已登记本记录，阅读顺序和维护约定同步更新。
