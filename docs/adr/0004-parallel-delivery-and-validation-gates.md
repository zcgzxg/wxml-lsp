# ADR-0004: 并行任务划分、交接契约与验收闸门

**Date**: 2026-11-15  
**Status**: accepted  
**Deciders**: 项目维护者、规划协作 agent

## Context

总体设计需要拆成可分发的并行子任务，而类型桥、语法输入、源码映射和编辑器同步相互影响。只按目录分工容易产生接口漂移、共享文件冲突和“各自测试通过但端到端失败”。当前项目只有工程与文本基础，不应将任务分解或有限实验描述成已完成产品。需要同时约定文件所有权、可 mock 的接口、关键风险验证和集成顺序。

## Decision

采用模块单一所有者、集成人维护公共边界、基础契约先行、mock 支持并行、关键验证闸门控制集成的方式交付。先证明真实类型与未保存同步，再扩展模板和常用语言功能；每项交付附可重复证据及支持/降级清单。本记录保存决策时的工作包基线，实际进度继续维护项目 README。

### 接口冻结分两次进行

- **C0 基础契约**：坐标单位、文件和版本身份、错误/能力状态、协议封装、mock 行为、共享样本编号。
- **C1 类型桥契约**：P4 验证后冻结 `CheckFragment` 的 JS/TS 方言约束、helper ABI、上下文接入和 shadow 布局。

P6 可在 C1 前开发绑定、作用域和映射测试，但不能将候选注入方案写成不可替换的公共接口。公共数据所有权和发布屏障遵循 ADR-0001 至 ADR-0003。

目录和 API 名称为规划范围，尚未存在的文件由对应工作包实施时创建。

| ID | 工作包 / 建议角色 | 修改范围 | 依赖 | 交付与验收 |
| --- | --- | --- | --- | --- |
| P0 | 集成与契约 / 主线程 | 根配置、公共契约、共享 fixtures、CI、文档入口 | 无 | C0、样本编号、mock 和依赖规则；P4 后收敛 C1；负责跨模块集成 |
| P1 | 文本坐标 / rust-tdd-guide | `crates/wxml-text/` | C0 | 字节/UTF-16 类型与转换；Unicode、CRLF、EOF、非法边界、可表示位置往返性质测试 |
| P2 | WXML 与表达式语法 / rust-tdd-guide | `crates/wxml-syntax/` | C0；接入 P1 | 容错语法树、表达式 parser、通用分段映射；正反例、输入中间态、增量/全量一致测试 |

| P9 | 常用语言功能 / 后续模块所有者 | metadata、styles 与对应 handler/query | 核心类型闭环 | 按 ADR-0001 的功能表逐项交付；具体文件分配后再启动并行 |

### 文件所有权与协作规则

1. 同一文件同一时间只有一个直接修改者；模块的公共入口和契约由其所有者维护。
2. 根 `Cargo.toml`、Cargo/Node lockfile、CI 和拟建共享 `tests/fixtures/` 由 P0 统一接收。工作包提交依赖及样本需求，不并发编辑这些文件。
3. Node 所有者不修改 Rust 类型层公共入口；Rust 所有者不为适配后端再实现一套脚本上下文桥。
4. 模块内部测试由模块所有者维护；跨模块 stdio 测试和共同验收场景由集成人组织。
5. 接口变更注明影响的工作包，先更新契约与 mock，再让依赖方接入；重要架构变化新增 ADR。
6. 临时实验只在仓库外运行，不在项目目录生成临时文件；临时目录不得作为项目证据的唯一来源。实验结论、环境、限制和最小可复查数据写入 ADR、`docs/reference/` 或提交说明；只有决定保留的实现、样本和测试进入仓库。过程证据不再单独保留目录，详见 [ADR-0005](0005-self-contained-project-documentation.md) 与 [ADR-0009](0009-project-slimming.md)。

### 执行波次

```text
P0 / C0
  ├─ P1 → P2 ────────────────────┐
  ├─ P3 ─────────────────────────┤
  ├─ P4 → C1 → P5 ───────────────┤
  └─ P7 最小服务 → P8 验证 ───────┤
          P2 + C1 → P6 ──────────┘
                    ↓
          stdio 类型闭环与一致性集成
                    ↓
          Zed 未保存编辑端到端验收
                    ↓
          完整作用域、组件属性与常用功能
```

P5/P6 可先借助 mock 准备工作，完整铺开前必须通过类型桥与 Zed 同步路径验证。发现关键路线失败时先收敛边界或更新 ADR，不让各任务自行采用互不兼容的替代方案。

### 集成闸门

| 闸门 | 通过条件 | 证据 |
| --- | --- | --- |
| G0：关键路线成立 | 普通 Page/Component 类型桥可用，Zed 的未保存同步路径成立 | P4 候选对比结果与 P8 实例/事件/版本记录 |
| G1：最小类型闭环 | 字段类型和说明来自真实声明，错误精确落在 WXML 字段上 | 真实 Node 后端加 stdio JSON-RPC 测试 |
| G2：编辑一致性 | 模板、脚本及 `data`/`properties` 类型声明的未保存变化传播，旧结果丢弃，修复后清除，重启可恢复 | 可控延迟测试与真实 Zed 编辑记录 |
| G3：模板语义 | 循环遮蔽、退出、条件链及适用窄化符合样本，未支持项明确 | 正反例 fixtures 与类型质量/检查状态断言 |
| G4：日常使用 | 补全、跳转、组件属性及所选常用功能逐项通过 | 功能回归与代表性项目人工验证 |

G0 可先用最小服务完成同步验证；它不是在所有模块完成后才补做的最终检查。G1 不等于完整 WXML 支持，G4 也不自动包含后置格式化或后端替换。

### 共同验收矩阵

以下场景均使用合成或获授权样本；必须断言具体行为和范围，不能只断言请求返回非空。

| 编号 | 初始场景与操作 | 预期结果及禁止副作用 | 验证方法 |
| --- | --- | --- | --- |
| AC-001 | 普通 Page 的 `data`、Component 的 `data` 引用跨文件 `User`；Component 的 `properties` 声明 `title`；hover `user.name`/`title` | 实际类型、原字段 JSDoc 和声明可追溯；不改源码、不强制 export | Node 类型桥与 stdio 测试 |
| AC-002 | 将 `user.name` 改为 `user.nmae`，再修复 | 只标错误字段，合法成员不误报，修复后旧诊断清除 | 精确文本范围与诊断集合断言 |
| AC-003 | 模板含中文、emoji、LF/CRLF，在字段处查询及编辑 | hover、错误和补全替换均对应正确字符，不拆代理对 | 单元/属性测试及 stdio 测试 |
| AC-004 | 未保存地修改 `data`/`properties` 字段类型（含其引用的跨文件类型）或仅修改 JSDoc | 模板结果随新依赖版本更新，无须保存或刷新模板 | backend host 测试与 Zed 实测 |
| AC-005 | 嵌套循环使用默认/自定义名字并遮蔽外层，随后退出 | 内层与外层类型符合各自绑定，循环变量不泄漏 | 作用域 IR 与正反例检查 |
| AC-006 | 可空或判别联合在 if/elif/else 中使用 | 合法分支访问通过，非法分支访问精确报错；未覆盖形式明确降级 | 检查片段快照与真实后端诊断 |
| AC-007 | JS 有 JSDoc 且 `checkJs=false`，模板检查策略启用 | 正确成员有类型和文档，错误成员有模板诊断，不重复发布无关 JS 错误 | 策略组合与类型桥测试 |
| AC-008 | 不同配置/路径别名/组件归属，以及相同脚本的不同视图 | 使用实际项目类型环境，视图和项目结果不串扰 | project/backend 集成测试 |
| AC-009 | 延迟旧请求后再次编辑，随后模拟后端退出 | 旧结果/ACK 不发布，失效状态可见，新世代重放后恢复 | 可控 mock、stdio 进程测试 |
| AC-010 | Zed 同时打开模板、页面/组件脚本及 `data`/`properties` 引用的类型声明文件，原主服务开启 | 未保存事件进入正确状态源，主服务正常，无重复无关诊断 | 实例/事件/版本日志及人工编辑 |
| AC-011 | 存在 any、缺少类型、未支持模板形式或 helper 错误 | 返回诚实的类型质量与检查状态，不把空结果当严格通过 | 能力状态与失败注入测试 |
| AC-012 | 自定义组件属性、事件和补全涉及反向编辑 | 按支持的绑定形式检查；定义回原文；不能安全映射的编辑不返回 | 功能测试与原文编辑结果断言 |
| AC-013 | 自定义组件在 `properties` 声明 `title`（含 `type`/`optionalTypes`/JSDoc），WXML hover `title` 并访问未声明属性 | 类型和说明来自实际 `properties` 声明，不按默认值猜测；未声明属性不伪造 | 类型桥、hover 文档与诊断断言 |

### 测试、度量和交付证据

- Rust 遵循项目 TDD 与检查规则：先有失败用例，再最小实现，运行 `cargo fmt`、`cargo check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`；以 CI 已配置的更完整检查为补充。
- 核心解析、坐标、映射和失效逻辑加入属性测试；沿用项目 80%+ 覆盖率目标，实际数值必须由覆盖率工具生成。
- Node 增加类型检查、宿主/桥接/映射单元测试、协议与重启测试，不能只依赖 Rust mock。
- 实施后按项目流程进行代码审查；提交前执行既有安全和依赖检查。这些是实施要求，不是本次文档记录已经执行的检查。
- 性能先测解析、后端查询和端到端 p50/p95、内存，注明硬件、文件规模和冷热状态，再制定预算；不编造固定完成时间或未经实测的延迟保证。
- 格式化、缓存精细化和替换 Node 后端后置。格式化必须有幂等、语义保真与解析失败不修改的测试；新后端通过同一验收矩阵后再决定替换。

每个工作包交付：变更文件、接口与版本、测试命令及结果、支持/降级清单、集成注意事项。没有实际执行证据的项目标为待验证，不以原项目测试或旧实验代替当前验收。

### 可直接用于派发的任务结构

```text
工作包：P编号、单一所有者
目标：可观察的用户或模块行为
范围：允许修改的目录和公共入口
前置：C0/C1、依赖工作包和有效 ADR
输入：契约版本、mock、样本编号和坐标约定
输出：接口、实现、测试、覆盖状态与交接说明
禁止：跨目录替换他人实现、改共享锁文件、伪造类型或省略版本校验
验收：对应 AC 编号、闸门、命令及实际结果
风险：未解决的问题与允许的降级方式
```

## Alternatives Considered

| 方案 | Pros | Cons | Why not |
| --- | --- | --- | --- |
| 所有模块同时全量实现 | 初始任务多 | 类型桥或平台失败后返工范围大 | 先验证关键路线，独立部分仍可并行 |
| 完全串行 | 集成冲突少 | 文本、项目、协议等独立工作被阻塞 | 用契约和 mock 支持安全并行 |
| 多任务共同修改公共入口/lockfile | 单任务推进方便 | 冲突和接口漂移难追溯 | 集成人统一接收共享变更 |
| 只验收 hover 非空或单元测试通过 | 执行成本低 | 漏检、错误位置、未保存失效和平台问题不可见 | 使用精确行为断言与编辑器证据 |

## Consequences

### Positive

- 可按文件范围和稳定契约直接派发任务，依赖关系可见。
- 高风险路线早验证，模块进展能够汇合到共同用户体验。
- 测试能够识别误报、漏检、版本错误和能力不足。

### Negative

- 集成人需要维护契约、mock、样本及共享文件，形成一定协调成本。
- 关键验证结果会限制部分任务的全量启动，不能只追求并行数量。
- 精确行为和编辑器验收比局部接口测试投入更多。

### Risks

- 共享接口形成瓶颈：C0/C1 分次冻结，变更列出受影响任务。
- 验证样本过窄：使用代表性真实写法补充矩阵，保留正反例和未支持清单。
- 文档被误认为进度：状态与测试证据仍维护在 README，不把 accepted 等同 implemented。

## Validation

派发前检查每包都有唯一修改者、可定位的输入输出、依赖、AC 和证据要求。扩大实现范围前检查 G0；产品能力按 G1 至 G4 分阶段声明。本 ADR 只记录方案，不新增实现、不运行上述功能验收。
